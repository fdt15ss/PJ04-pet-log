# AI Agent 개발자 면접 질문과 모범 답안

## 1. 문서 목적

이 문서는 Pet Log 프로젝트를 기반으로 AI Agent 개발자 면접을 준비하기 위한 예상 질문과 답변을 정리한다.

특히 다음 두 개념을 구분해서 설명하는 것을 목표로 한다.

- **개발 하네스**: AI 에이전트가 기획, 설계, 구현, 검증을 안정적으로 수행하도록 만드는 작업 환경과 피드백 루프
- **제품 Agent Runtime**: Pet Log 서비스에서 사용자 요청을 처리하는 LangGraph 기반 기록 분석 및 제안 파이프라인

면접에서는 단순히 "하네스 엔지니어링을 사용했다"고 말하기보다, 어떤 역할과 산출물, 검증 게이트를 설계했는지 구체적으로 설명해야 한다.

## 2. 1분 프로젝트 소개

> Pet Log는 반려동물의 자연어 기록을 구조화하고, 최근 기록과 결합해 상태 변화, 위험 신호, 관리 제안, 리마인더로 연결하는 AI Agent 서비스입니다.
>
> 제품 내부 Agent Runtime은 LangGraph 기반 상태 그래프로 구성했고, LangChain은 모델, 도구, 미들웨어 어댑터로 사용했습니다.
>
> 개발 과정에서는 하네스 엔지니어링을 적용해 Product Planner, UX Designer, AI Agent Designer, Orchestrator, QA Reviewer 역할을 분리했습니다. 각 에이전트가 자유롭게 작업하게 두지 않고, MVP 범위, UX 흐름, AI 안전 사양, 구현 계획, QA 결과를 순차 산출물로 남기고 Producer-Reviewer 게이트를 통과하도록 했습니다.
>
> 특히 반려동물 건강 도메인이기 때문에 확정적 진단을 금지하고, 구조화 출력, 쓰기 작업 확인, fallback, E2E eval을 통해 모델의 비결정성을 통제하는 데 중점을 뒀습니다.

## 3. 핵심 예상 질문과 모범 답안

### 3.1 AI Agent와 일반적인 LLM 호출은 무엇이 다른가요?

일반적인 LLM 호출은 입력에 대해 한 번 응답하는 데 가깝다. 반면 Agent는 목표를 달성하기 위해 상태를 유지하고, 도구를 선택하며, 여러 단계를 실행하고 결과에 따라 다음 행동을 결정한다.

Pet Log에서는 `입력 구조화 → 컨텍스트 조회 → 위험 탐지 → 저장 → 제안 → 리마인더`가 이어지기 때문에 단일 프롬프트보다 상태 기반 Agent workflow가 적합했다.

### 3.2 하네스 엔지니어링을 어떻게 정의하나요?

하네스 엔지니어링은 모델 자체를 바꾸는 일이 아니라, 모델이 안정적으로 일을 수행하도록 주변 실행 환경을 설계하는 일이다. 명확한 작업 명세, 저장소 내 지식, 도구 권한, 단계별 산출물, 평가, 관측, 재시도 및 사람의 승인 과정이 포함된다.

핵심은 더 좋은 프롬프트 하나를 만드는 것이 아니라, 실패가 발견되고 수정되는 시스템을 만드는 것이다.

### 3.3 Pet Log에서는 하네스를 구체적으로 어떻게 구성했나요?

Pipeline과 Producer-Reviewer 패턴을 사용했다.

- Product Planner: MVP 범위와 acceptance criteria 정의
- UX Designer: 모바일 우선 화면 흐름과 상태 정의
- AI Agent Designer: 입력, 분석, 제안, 안전 경계 정의
- Orchestrator: 선행 산출물과 저장소 상태를 바탕으로 구현 계획 작성
- QA Reviewer: 전체 산출물의 범위, 일관성, 안전성 검토

단계별 결과는 `_workspace/01`부터 `05`까지 파일로 남겨 다음 에이전트가 명시적으로 읽도록 했다. QA 결과가 `fix`이면 영향을 받는 최소 산출물을 수정하고, `redo`이면 구현을 시작하지 않도록 했다.

### 3.4 하나의 강력한 에이전트에게 모든 작업을 시키면 안 되나요?

작은 작업은 단일 에이전트가 더 효율적이다. 하지만 기획, UX, AI 안전, 구현, QA처럼 실패 원인이 다른 작업을 한 에이전트가 한 번에 처리하면 범위 누락과 자기검증 편향이 커질 수 있다.

따라서 모든 작업을 멀티 에이전트로 만들지 않고, 독립적인 검증 기준과 명시적인 인수인계가 필요한 단계만 역할을 분리했다.

### 3.5 하네스와 LangGraph는 어떤 차이가 있나요?

하네스는 개발 프로세스와 에이전트 작업 환경 전체를 의미한다. 반면 LangGraph는 실제 제품에서 상태 기반 Agent workflow를 실행하는 런타임이다.

- 하네스: AI가 이 프로젝트를 어떻게 개발하고 검증할 것인지 통제
- LangGraph: 사용자 요청이 들어왔을 때 제품 Agent가 어떤 순서로 실행될 것인지 통제

이 둘을 구분하지 않으면 개발 자동화 에이전트와 제품에 포함된 AI Agent가 같은 것처럼 들릴 수 있다.

### 3.6 LangGraph를 선택한 이유는 무엇인가요?

Pet Log 기록 분석은 단계별 상태 전이와 조건부 분기가 분명했다. 각 단계를 노드로 분리하면 실패 위치와 중간 상태를 추적하기 쉽고, 특정 단계만 재시도하거나 향후 사람의 승인을 추가하기도 쉽다.

다만 LangGraph를 사용했다는 사실 자체가 장점은 아니다. 중간 상태, 재개, 분기, 관측이 필요한 workflow인지 먼저 판단하고 도입해야 한다.

### 3.7 모든 기능에 LangGraph를 사용했나요?

모든 기능에 사용하지 않았다. 상태 전이가 길고 여러 외부 호출을 조정해야 하는 기록 분석과 쇼핑 추천에는 LangGraph를 적용했다.

반면 병원 추천처럼 응급 여부 판단, 검색, 정렬 정도로 흐름이 비교적 짧은 기능은 일반 application agent와 provider 조합으로 유지했다. 그래프 사용 여부는 기능 이름이 아니라 상태, 분기, 복구 요구를 기준으로 결정했다.

### 3.8 LangChain과 LangGraph의 역할은 어떻게 나눴나요?

LangGraph는 workflow와 상태 전이를 담당했다. LangChain은 모델 호출, structured output, tool adapter, retry 같은 모델 주변 기능에 사용했다.

도메인 계층이 특정 프레임워크 타입에 직접 의존하지 않도록 LangChain과 LangGraph 의존성은 infrastructure와 agent runtime 경계에 격리했다.

### 3.9 Agent의 상태는 어떻게 설계했나요?

자연어 원문, 구조화된 기록 후보, 반려동물 프로필, 최근 기록, 위험 신호, 제안, 저장 결과처럼 다음 단계가 실제로 필요로 하는 데이터만 상태에 포함했다.

포맷된 문장보다 원본 또는 구조화 데이터를 상태로 보관해야 다른 노드가 재사용하기 쉽고 디버깅도 가능하다. 불필요한 전체 대화 기록은 컨텍스트 비용과 오류 전파를 늘리므로 제외하는 것이 좋다.

### 3.10 Tool은 어떻게 설계했나요?

프로필 조회, 최근 기록 조회, 기록 저장, 일정 조회처럼 하나의 명확한 책임을 갖도록 만들었다. 입력과 출력은 스키마로 제한하고, 조회 도구와 쓰기 도구를 구분했다.

Tool Registry에서는 중복된 tool name을 거부해 Agent action space 충돌을 방지했다. 쓰기 도구에는 조회 도구보다 더 강한 승인과 검증 정책을 적용할 수 있도록 경계를 분리했다.

### 3.11 Structured Output이 왜 중요한가요?

자연어 출력만 사용하면 저장 단계에서 필드 누락이나 타입 오류가 발생할 수 있다. 기록 카테고리, 제목, 상세 내용, 상태처럼 애플리케이션이 소비하는 결과는 스키마 기반 structured output으로 받았다.

다만 스키마 검증 통과가 의미 정확성까지 보장하지는 않는다. 따라서 structured output 검증과 별도로 capability eval과 도메인 규칙 검사가 필요하다.

### 3.12 환각은 어떻게 줄였나요?

환각을 완전히 제거한다고 표현하지 않고, 발생 가능성과 피해 범위를 통제한다고 접근했다.

- 구조화 출력 적용
- 허용된 라우트와 도구 제한
- 최근 기록 기반 컨텍스트 사용
- 규칙 기반 위험 탐지 병행
- 모델 실패 시 결정론적 fallback 제공
- 건강 관련 확정적 진단 금지

근거가 부족한 경우에는 추가 관찰이나 전문가 상담을 안내하도록 안전 경계를 설정했다.

### 3.13 의료 및 건강 도메인 안전은 어떻게 처리했나요?

Agent가 수의사를 대체하지 않는다는 비목표를 명시했다. 증상을 질병으로 확정하지 않고 위험 신호와 관찰 필요성을 구분하며, 응급 가능성이 있으면 상품 추천보다 병원 안내를 우선하도록 했다.

QA 단계에서는 확정적 진단, 근거 없는 안심, 위험 상황에서의 상업적 추천을 구현 중단이 필요한 `redo` 조건으로 설정했다.

### 3.14 Human-in-the-loop는 어디에 필요한가요?

모든 단계에 승인을 넣으면 사용자 경험이 나빠지므로 부작용이 있는 작업에만 적용해야 한다. Pet Log에서는 기록 저장과 같은 쓰기 작업, 정보가 모호한 기록, 외부 행동을 발생시키는 작업이 주요 후보이다.

조회와 분석은 자동 수행하되, 되돌리기 어렵거나 신뢰도가 낮은 작업은 중단하고 사용자의 확인을 받는 방식이 적합하다.

### 3.15 실패와 재시도는 어떻게 처리했나요?

실패 유형을 구분해서 처리해야 한다.

- 네트워크 및 rate limit 오류: 제한적인 재시도
- 잘못된 스키마 출력: 검증 오류를 포함해 재요청
- 사용자 정보 부족: 추가 입력 요청
- 복구 불가능한 provider 오류: 안전한 fallback 반환
- 쓰기 작업 실패: 중복 실행을 막기 위한 idempotency 적용

재시도 횟수와 timeout을 제한하지 않으면 비용과 응답 지연이 연쇄적으로 증가할 수 있다.

### 3.16 모델 fallback은 어떻게 구성했나요?

Provider 경계 뒤에 primary와 fallback 모델을 구성해 애플리케이션 로직이 특정 모델에 결합되지 않도록 했다. Primary가 일시적인 오류로 실패한 경우에만 fallback으로 넘어가도록 하고, 모델 전환 여부를 로그로 남기는 구조이다.

Fallback 모델은 단순히 더 저렴한 모델을 선택하는 것이 아니라 structured output 지원, 지연 시간, 비용, 품질 기준을 함께 확인해야 한다.

### 3.17 Agent를 어떻게 평가했나요?

일반 소프트웨어 테스트와 Agent eval을 구분했다.

- 단위 테스트: 정책과 변환 로직의 결정론적 정확성 확인
- 통합 테스트: Agent, provider, repository 사이 계약 확인
- Capability eval: 다양한 자연어 기록이 올바른 구조와 위험 수준으로 변환되는지 확인
- Regression eval: 프롬프트나 모델 변경 후 기존 성공 사례가 깨지지 않았는지 확인
- E2E eval: 실제 사용 흐름, 모바일 overflow, client error, 기록 저장 흐름 확인

프런트엔드에서는 `npm run eval`로 모바일 UI 검사와 기록 저장 flow grader를 실행할 수 있도록 구성했다.

### 3.18 어떤 평가 지표를 사용해야 하나요?

작업별 실패 비용을 고려해 지표를 선택해야 한다.

| 대상 | 주요 지표 |
| --- | --- |
| 기록 구조화 | 필드 정확도, 스키마 통과율, 누락률 |
| 위험 탐지 | Recall, False Negative Rate, Precision |
| 추천 | 관련성, 근거 일치도, 중복률 |
| 운영 | End-to-end latency, tool failure rate, fallback rate |
| 비용 | 요청당 token, 모델 비용, 평균 재시도 횟수 |

건강 위험 탐지는 일반 정확도보다 false negative 비용이 크므로 recall을 더 중요하게 봐야 한다.

### 3.19 Agent의 관측 가능성은 어떻게 확보하나요?

요청 단위 trace ID를 부여하고, 각 노드의 시작과 종료, 지연 시간, 사용 모델, 호출 도구, 재시도, fallback 여부를 구조화 로그로 남겨야 한다.

개인정보와 원본 tool argument는 그대로 로그에 남기지 않고 마스킹해야 한다. 최종 응답만 기록하면 실패가 프롬프트, 모델, tool, 외부 API 중 어디서 발생했는지 알기 어렵다.

### 3.20 비용과 응답 속도는 어떻게 최적화하나요?

먼저 전체 workflow를 측정해 병목 노드를 찾는다. 규칙으로 충분한 위험 탐지나 데이터 정규화는 코드로 처리하고, 의미 판단이 필요한 단계에만 LLM을 사용한다.

단순 분류 및 추출 작업과 복잡한 추론을 분리해 모델을 라우팅하고, 컨텍스트 축소, 검색 결과 캐싱, 독립 노드 병렬 실행 등을 적용할 수 있다. 최적화 전에는 반드시 품질 기준과 baseline을 먼저 정의해야 한다.

### 3.21 RAG가 반드시 필요한가요?

모든 Agent에 RAG가 필요한 것은 아니다. 사용자 기록 구조화는 현재 입력과 스키마만으로 가능하지만, 건강 지식에 근거한 답변은 검증된 외부 자료가 필요하므로 RAG의 가치가 크다.

RAG를 도입할 때는 검색됐다는 사실보다 출처 승인, 최신성, chunk 품질, retrieval hit, 답변과 근거의 일치도를 평가해야 한다.

### 3.22 Prompt Injection은 어떻게 방어하나요?

사용자 입력, 검색 문서, tool 결과를 모두 신뢰할 수 없는 데이터로 취급해야 한다. 시스템 규칙과 외부 문서를 분리하고, 검색 문서 안의 명령을 실행 지시로 해석하지 않도록 한다.

Tool allowlist, 인자 스키마, 사용자별 권한 검사, 쓰기 도구 승인, 호출 횟수 제한을 함께 적용해야 한다. 프롬프트만으로 보안을 해결하려고 해서는 안 된다.

### 3.23 가장 큰 설계 실수나 개선 경험은 무엇인가요?

초기에는 미래 확장을 고려해 Protocol, wrapper agent, 구현되지 않은 skeleton을 많이 만들었다. 하지만 MVP에서는 단순히 provider를 한 번 호출하는 wrapper까지 Agent로 분리하면서 파일 탐색 비용과 구조 복잡도가 커졌다.

이후 Agent 계층은 상태 관리, tool 선택, retry, 분기처럼 실질적인 orchestration 책임이 있을 때만 유지하고, 단순 위임은 pipeline이나 provider로 축소했다. 이를 통해 Agent 시스템에서도 추상화 수보다 실제 실행 경로의 명확성이 중요하다는 점을 배웠다.

### 3.24 운영 환경으로 확장한다면 무엇을 먼저 하겠습니까?

다음 순서로 개선할 수 있다.

1. Eval dataset과 기준 점수를 CI gate로 연결한다.
2. 노드별 tracing과 비용 및 fallback 대시보드를 구성한다.
3. 체크포인트 저장소와 idempotency를 추가한다.
4. 중단된 workflow를 안전하게 재개하도록 만든다.
5. 실제 사용자 피드백과 실패 데이터를 regression eval에 반영한다.

기능을 더 추가하기보다 현재 기능의 실패를 측정하고 재현할 수 있게 만드는 것이 우선이다.

### 3.25 하네스 엔지니어링에서 본인이 한 핵심 기여는 무엇인가요?

에이전트에게 단순히 작업을 지시한 것이 아니라 역할별 입력, 출력 계약과 완료 조건을 정의했다. 특히 AI 안전 사양이 구현 계획과 QA까지 누락 없이 전달되도록 산출물 순서를 만들고, `fix`와 `redo` 조건을 구분했다.

또한 테스트, lint, typecheck, E2E, eval을 실행 가능한 검증 명령으로 만들어 에이전트의 완료 주장보다 실제 검증 결과를 완료 기준으로 사용했다.

## 4. 압박 및 꼬리 질문

### 4.1 결국 멀티 에이전트로 문서를 만든 것 아닌가요?

문서 생성 자체가 목적은 아니다. 산출물이 다음 단계의 입력 계약이 되고, QA가 구현 진입 여부를 결정하며, 실행 가능한 테스트가 최종 게이트가 된다는 점이 핵심이다.

### 4.2 에이전트 수가 많을수록 좋은가요?

아니다. 역할 분리로 얻는 검증 효과보다 컨텍스트 전달 비용과 조정 비용이 커지면 단일 에이전트가 더 낫다. 독립적인 책임, 검증 기준, 인수인계가 있을 때만 분리해야 한다.

### 4.3 Agent라고 했지만 사실 workflow 아닌가요?

핵심 기록 파이프라인은 예측 가능성과 안전을 위해 workflow 성격을 강하게 유지했다. 제한된 구간에서만 모델 판단과 tool 선택을 허용한 bounded agent 구조라고 설명하는 것이 정확하다.

### 4.4 LangGraph 없이도 구현할 수 있지 않나요?

가능하다. 단순 선형 처리라면 일반 함수 조합이 더 단순하다. Pet Log에서는 단계별 상태, 분기, 관측, 재개 가능성이 필요한 흐름에만 LangGraph를 선택했다.

### 4.5 하네스를 적용해서 실제로 무엇이 좋아졌나요?

범위 누락과 AI 및 UX 사양 불일치를 구현 전에 발견할 수 있었고, 작업 완료 기준이 에이전트의 서술이 아니라 산출물과 테스트 결과로 바뀌었다.

### 4.6 정량적인 개선 수치가 있나요?

실제로 측정하지 않은 숫자를 만들어 답하면 안 된다. 현재 수치가 없다면 QA 재작업 건수, eval 통과율, 평균 retry, fallback rate, 작업 리드타임처럼 측정할 지표와 수집 방법을 설명하는 것이 좋다.

### 4.7 LLM이 잘못된 tool을 반복 호출하면 어떻게 하나요?

Tool call 횟수와 전체 step 수를 제한하고, 동일 인자를 반복 호출하는 패턴을 탐지한다. 반복 실패 시 fallback으로 종료하거나 사람에게 제어를 넘긴다. 쓰기 tool은 idempotency key로 중복 부작용을 차단해야 한다.

### 4.8 모델을 변경하면 무엇을 다시 검증해야 하나요?

Structured output 호환성, tool 선택 정확도, safety instruction 준수율, latency, 비용을 다시 측정해야 한다. 기존 eval dataset을 기준으로 baseline과 비교하고, 개선된 평균 점수뿐 아니라 새롭게 발생한 회귀 사례도 확인해야 한다.

## 5. 면접에서 피해야 할 표현

| 피해야 할 표현 | 더 정확한 표현 |
| --- | --- |
| 멀티 에이전트를 사용해서 정확도가 높아졌다 | 역할 분리 전후의 eval 결과로 개선 여부를 검증했다 |
| 환각을 제거했다 | 환각 발생 가능성과 피해 범위를 줄였다 |
| LangGraph라서 확장성이 좋다 | 상태, 분기, 복구 요구 때문에 LangGraph를 선택했다 |
| 모든 기능을 Agent로 만들었다 | Agent 책임이 필요한 흐름에만 적용했다 |
| 하네스 엔지니어링은 프롬프트 엔지니어링이다 | 환경, 도구, 평가, 관측, 피드백 루프를 함께 설계했다 |
| 구현 예정인 기능을 운영했다 | 실제 실행 경로와 experimental 또는 planned 기능을 구분했다 |

## 6. 답변 구성 공식

기술 질문에는 다음 순서로 답하면 설명이 명확해진다.

1. **문제**: 어떤 불확실성과 실패 가능성이 있었는가?
2. **선택**: 어떤 구조나 기술을 선택했는가?
3. **이유**: 다른 대안보다 왜 적합했는가?
4. **검증**: 테스트 또는 eval로 무엇을 확인했는가?
5. **한계**: 현재 구현의 한계와 다음 개선점은 무엇인가?

예시는 다음과 같다.

> 자연어 기록은 출력 형식이 흔들려 저장 단계에서 오류가 발생할 수 있었습니다. 그래서 structured output과 스키마 검증을 적용했습니다. 일반 텍스트 파싱보다 필드 계약을 명확하게 유지할 수 있었고, 정상 입력과 누락 입력을 eval dataset으로 검증했습니다. 다만 스키마 통과가 의미 정확성을 보장하지는 않아서 도메인 평가가 추가로 필요합니다.
